## 1. 对齐原则：只对齐「语义层」，不统一「执行层」

| 层 | 对齐什么 | 是否做 |
|---|---|---|
| **L1 语义字典** | 算子名 / 字段名 / 轴语义（time/cross/element）/ 窗口参数化 | ✅ **立即做**（纯数据 yaml，零风险） |
| **L2 记录 schema** | 因子记录字段 + 指标口径（多池 × 多频率 × 成本） | ✅ 中期做（并进对方 M4） |
| **L3 执行引擎** | 用同一套求值后端（二选一） | ❌ **不做** |

**为什么不做 L3**：loop_code 要跑几十万候选，必须用自研快速引擎（批量向量化，比逐个 evaluate 快 30x）；
qlib 表达式引擎是为"少量因子、精确回测"设计的。强行统一 = 拖死挖掘侧。
**只在"已入库因子"这个出口做双跑回归**（同区间/同 label/同池，容差 <1e-6），不一致的先查 §2.3 的三个坑。

## 2. 算子与字段字典

### 2.1 算子映射（loop_code → qlib ops）

| loop_code | qlib_code | 备注 |
|---|---|---|
| `ts_mean{w}(x)` | `Mean(x, w)` | 1:1 |
| `ts_std{w}(x)` | `Std(x, w)` | 1:1 |
| `ts_max{w}` / `ts_min{w}` | `Max(x, w)` / `Min(x, w)` | 1:1（**都是滚动**） |
| `ts_sum{w}` | `Sum(x, w)` | 1:1 |
| `ts_rank{w}` | `Quantile(x, w)` | ⚠ 语义**待确认** |
| `ts_delay{n}` | `Ref(x, n)` | 1:1 |
| `ts_delta{n}` | `Sub(x, Ref(x, n))` | 组合 |
| `corr{w}(a, b)` | `Corr(a, b, w)` | 1:1 |
| `add/sub/mul/div` | `Add/Sub/Mul/Div` | 1:1 |
| `log` | `Log` | 1:1 |
| `abs` / `neg` / `sign` | `Abs` / `Mul(-1,·)` / `SGN` | `SGN` 对方已有外挂 |
| `cs_rank` | `Rank` | 截面，1:1 |
| `cs_demean` | 需外挂或对方截面算子 | ⚠ **待确认** |
| `cs_scale` | 需外挂 | ⚠ **待确认** |
| **`max(a,b)` / `min(a,b)`（逐元素）** | **qlib 无** | ⚠ **最危险，见 §2.3** |

| loop_code 叶子 | qlib_code | 备注 |
|---|---|---|
| `close/open/high/low/volume/vwap` | `$close/$open/$high/$low/$volume/$vwap` | 1:1 |
| `turnover`（成交额，元） | `$amount` 或 `$vwap × $volume` | ⚠ 待确认 |

| `mf_{s,m,l,x}_{buy,sell}`（金额，万元×1e4） | `L2_AMO(4/3/2/1, b/s)` | ✅ **同源 moneyflow3**，档位 s/m/l/x ↔ 4/3/2/1 |
| `mf_{s,m,l,x}_{bqty,sqty}`（手×100） | `L2_VOL(4/3/2/1, b/s)` | ✅ 同源 |
| `barra_*`（11 个） | **无对应数据源** | ❌ 走"值对齐"通路（§1 双通路） |
| `fa_*`（8 个财报 PIT） | **待确认** | ⚠ |

### 2.3 三个语义坑（对齐时最容易静默出错）

1. **`max/min` 语义完全相反**：loop_code 是**逐元素**取大；qlib 的 `Max(x,N)` 是 **N 日滚动**。
   直接翻译会算错且不报错。必须外挂 `EMax/EMin`，或渲染成 `If(Gt(a,b), a, b)`。
   本库最常用的 `max(·, barra_residual_volatility)` 骨架会全面踩此坑。
2. **停牌语义**：loop_code 保留 NaN 行 + `buyable/next_sell` 处理；qlib_code 用 `SR()` **删行**
   （连续交易日语义，复牌首日 `Ref` 不 NaN）→ **同一因子两边数值必然不同**。
3. **评估口径**：持有期（loop 5/15 vs 对方 1/5/20）、分组（**十档 vs 5 组**）、
   成本（loop 往返 0.5% vs 对方未定）、池（loop 多池 vs 对方单池）。
   **不对齐这一层，算子翻译对了结果仍对不上。**

### 2.4 双通路（资产边界）

- **通路 A · 表达式对齐**：量价 + 资金流因子（叶子在双方都存在）→ 翻译成 qlib 表达式，由对方算。
- **通路 B · 值对齐**：含 **BARRA / 财报PIT** 的因子（对方无数据源）→ 由 loop_code 算好值，
  按对方 h5 规范写入 `factor_lib/factors/`，对方只读「值 + meta.json」。

### 3.0.1 成本档定义与「门槛边际」风险（2026-09-11 定稿，经两次更正）

**成本扣在「单向换手率」上**（`rt - (1-keep)*cost`，`turn = 1 - keep`）。各档语义如下：

| 档 | 值 | 构成 | 定位 |
|---|---|---|---|
| 实盘（滑点千1.5） | `0.0046` | 佣金**万三**×2 + **滑点千1.5×2** + 卖出印花税千1 | 实盘参考 |
| 实盘（滑点千2） | `0.0056` | 同上，滑点千2 | 实盘参考（滑点偏高情形） |
| **`loop_engine` CLI `--cost` 默认** | **`0.004`** | 代码注释写"佣金千1.5×2+印花税千1"，但**实际意图 = 「实盘略宽松一丢丢、取整数」**（用户 2026-09-11 说明） | **主用档**（≈实盘的 0.87x） |
| `standard_test.py` `--cost` 默认 | `0.007` | 佣金千1.5×2 + 滑点千1.5×2 + 印花税千1 | **压力测试档**（≈实盘 1.5x，**刻意设高**，用于最后压测） |
| `factor_miner.COST_RT`（`evaluate_real` 默认参数） | `0.005` | 佣金千2×2 + 印花税千1 | 保守 |

> **勘误记录（本节同日改过两次，留痕以免再犯）**
> ① 初稿把 `0.007` 当"经济上正确的往返成本"，断言"引擎 `0.004` 低估 43%" → **错**（0.007 是压测档）。
> ② 二稿据此把"真实成本"算成 `0.0016`（只算佣金+印花税、**漏了滑点**）→ 也**错**。
> ③ 定稿：**实盘必须含滑点**（用户口径：单边千1.5~千2 是常态）→ 实盘 ≈ `0.0046~0.0056`；
> **引擎 `0.004` 是有意取的"略宽松整数档"，不是漏算**。
> 结论：**数字都对，是我的两次解读错了**——教训是**成本档的"构成"必须写清，否则会被误读**。

#### ★ 真正重要的发现：L2 硬门槛在这批因子上是「擦线」的

实盘档 `0.0046` 实测（`ai_test/run_standard_batch.py --cost=0.0046`，报告前缀 `live_F*`）：

| f5 指标 | F25 | F26 | F27 | F28 | F29 | F30 |
|---|---|---|---|---|---|---|
| 超额 @**0.0046** | 5.15% | 7.48% | 3.60% | 4.73% | 3.45% | 4.55% |
| **Calmar @0.0046** | **1.18** | **0.54** | **0.50** | **0.47** | **0.43** | **0.46** |
| （对照）Calmar @0.004 | 1.28 | 0.63 | 0.61 | 0.55 | 0.52 | 0.52 |
| 过 L2 门槛 `calmar>0.5`？ | ✅ 稳 | ⚠️ 擦线 | ⚠️ **正中门槛** | ❌ | ❌ | ❌ |

**成本只差 `0.0006`（+15%），`3/6` 因子从"过"变成"不过"。**

- 根因：本批 Calmar 在引擎档下全挤在 **0.52~0.63** 的窄带里，**恰好压在 `calmar > 0.5` 门槛上**。
  门槛附近的判据对假设极度敏感 → 这是**判据设计问题**，不是因子问题。
- **F25 是唯一远离门槛的**（1.28 → 实盘 1.18 → 压力档 0.70，全程最稳且市值中性），
  独立印证平台侧把它列为 T1 的判断。
- **对引擎的改动（补进 P4）**：L2 不应只看"是否过线"，应看**边际**：
  ① 要求**实盘档与压力档双档都过线**（或记 `calmar` 相对门槛的裕度）；
  ② 报告因子时**同时给出实盘档指标**，避免只报 0.004 口径（本批 3/6 是擦线过）。

#### 频率结论（在实盘~引擎档区间是稳的）

`10 日优于 5 日` 的比例随成本档变化：压力档 `0.007` 6/6 → 引擎档 `0.004` **5/6** →
实盘档 `0.0046` **5/6**（F27 例外：0.50→0.44）→ 若成本继续降到不含滑点口径可到 4/6。
→ **在实盘~引擎这个现实区间里，「10 日优于 5 日」是 5/6，结论可用**；
但 **`freq` 本质是成本假设的函数，不能当"因子属性"**——P0 提案的"多频率联合判据"阈值须绑定成本档。

#### 标签必须修（它已经误导过一次）

`loop_engine` 的 `--cost` help 写 `往返成本, 默认单边千1.5=0.004`（"往返/单边"混用）；
日志打 `[cost=4.0bp/边]`；`factor_library.md` 写"成本 4bp/边"。
**`0.004` 既不是"单边"，也不该叫"bp/边"**——它是一个**"实盘略宽松"的往返取整档**。
建议改成：`--cost 往返成本(已含滑点)；默认 0.004 = 实盘(0.0046)略宽松取整；'压力档 0.007'`。

### 3.1 分箱：十档 vs 5 组 —— **这不是"折中"，是两个用途**

- **十档（10 档）用于筛选与诊断**。本库 `standard_test.py` 的判读规则明确依赖它：
  `⚠️ D1<D2: 最极端档反而更差(顶档被污染), 宜剔D1或用D2`。
  **降到 5 档会把这个决策依据平均掉。**
- **5 组用于看板展示**（对齐聚宽 factorlib 的"单调性"口径），每组样本翻倍、更稳。
- **结论**：内部诊断保 **十档** + 看板给 **5 组** + 另报 Top10%/Bottom10% 多空。
  同一份因子值可任意分组，**并存成本为零，不需要二选一**。
- ⚠ **分箱数与存储/性能无关**（存的是原始因子值）。**不要把 5 档桶号当存储**（见 §4.4）。

| **npy mmap（两种轴序均同）** | 50.0 | ~0.0 | ~0.0 | 0.2 | ~0.0 | 12~13 |
| **h5 (date,inst) 连续 / 不压缩** | 50.0 | **0.4** | 3.6 | 2.5 | 32.7 | **18.0** |
| h5 (date,inst) chunk=1日 + lzf | 48.3 | 0.1 | 10.6 | 1.3 | 285 | 63.6 |
| **h5 (inst,date) 连续（设计稿默认）** | 50.0 | **151.5** | 19.0 | 812.6 | 0.1 | 17.0 |
| pq_wide (inst行, date列) zstd | 62.5 | 2.7 | 14.8 | 11.3 | 282 | 66.4 |
| pq_long zstd (rg=1日) | 110.8 | 1.7 | 31.9 | 10.1 | 978 | 152 |

**结论**：
1. **500x 差距的根因是 HDF5 实现**（非连续 hyperslab 退化成整数据集扫描），**不是轴序本身**——
   同样的 `(inst,date)`，裸 memmap 取列只需 ~0.0ms。准确表述：**HDF5 未分块时轴序要命；有合适 chunk / 裸 memmap 时不要命**。
2. 但对方设计稿 §7.2 的 `data=(instrument × datetime)` 仍应改成 `(datetime × instrument)`：
   HDF5 里让主导访问变成**连续行**才是关键。
3. **chunk 是零和的**：优化单日读必然牺牲全量读（63.6 vs 18.0）或单股全史。
4. **`(date,inst)` 连续 + 不压缩 + 每因子一 h5** = HDF5 家族综合最优。

### 4.2 真实因子字节成本（`ai_test/bench_real_factor_bytes.py`，L1 子面板 2094日×2000股，真实 NaN 17~28%）

| 编码 | F14 | F20 | F23 |
|---|---|---|---|
| h5 raw float32 | 16.75 (1.0x) | 16.75 (1.0x) | 16.75 (1.0x) |
| h5 lzf | 13.87 (1.21x) | 12.66 (1.32x) | 8.98 (1.87x) |
| h5 gzip9 | 12.32 (1.36x) | 11.04 (1.52x) | 7.19 (2.33x) |
| parquet zstd 宽表 | 16.92 (**0.99x**) | 15.29 (1.10x) | 9.82 (1.71x) |
| h5 float16 | 8.38 (2.00x) | 8.38 (2.00x) | 8.38 (2.00x) |
| **h5 uint8 截面分位 + gzip9** | **3.02 (5.54x)** | **2.92 (5.74x)** | **3.28 (5.11x)** |

**结论**：
1. **真实连续因子压缩比 1.2~2.3x**（人造随机浮点是 1.04x）—— 比"不可压"好，但**不是"高得多"**。
2. **0/1 触发型 gzip 可达 68.7x**（16.75MB → 0.24MB，触发率 8.29%）——**该结论成立，
   但只适用于平台侧（qlib_code 的益盟/通达信公式因子）**；本库算子集无比较/布尔算子，
   结构上产不出 0/1 因子。**两边压缩结论不能互换。**
3. **直觉陷阱**：触发率 8.29% 时，稠密 gzip（0.24MB）比稀疏 `(t,i)` 索引（2.78MB）**省 11 倍**
   ——"0/1 就存稀疏"是陷阱，稀疏只在触发率 **<1%** 时才划算。
4. **真正的省空间杠杆是量化，不是压缩**：`uint8`（256 级）截面分位 = 4.19MB raw / 2.9~3.3MB
   compressed（**5.1~5.7x**），比 float32 任何压缩好一倍，且**保住截面排序语义**（IC/分组/多空近乎无损）。

### 4.3 结论与落地格式

```
factor_lib/factors/
  a3/                      # 按 ast_hash 前 2 位分桶(防单目录 30 万文件退化)
    F23/
      values.h5            # dataset 'data' = float32 (n_date, n_inst)，连续、无 chunk、不压缩
                           # attrs: dates, instruments, freq, unit, ast_hash, version,
                           #        source(genN/manual), created_at, sign, leaf_set, fam_key
```

- 备选：裸 `.npy` memmap 更快（全项 ~0.0ms）但无自描述 → 需 sidecar json。
- **封装成 `FactorStore` 抽象**（`day / window / inst / full / meta` 五个接口），格式被接口挡住，
  将来换 parquet 只加一个类；**用 §4.1 的基准脚本当验收测试**（已内置正确性校验）。
- ⚠ **单股全史**在 `(date,inst)` 下慢（33ms~1s）。看板若要画"某股票因子走势"，
  建一份 `(inst,date)` 副本或缓存，**别为它牺牲主访问模式**。

### 4.4 不要做的事

- ❌ **不要抄 qlib 的 `.bin` 布局**：`{instrument}/{field}.{freq}.bin`（raw float32，首 float 为起始
  日历索引）是"每股票每字段一文件"——为"取某只股票一段行情"设计。25 因子 × 5570 股 = **14 万文件**，
  横截面读要开 5000 个文件。**这正是 qlib 自己算因子分析慢的根因。**
  （对方已在 `panel_expr._field_bin_meta` 上付过一次优化成本来绕开它。）
- ❌ **不要用 Parquet**：1.25~2.2x 体积、读慢 4~30x，其三件法宝（列裁剪/分区/谓词下推）在
  "每因子一文件、只有一列有值、随机浮点不可跳"的场景全部失效。除非将来要 DuckDB/BI 直接 SQL 查。
- ❌ **不要把 5 档桶号当存储**：丢组内排序 → 无法重算 IC（秩相关需完整排序）、无法改分组、
  无法回归/中性化 → **不可逆的信息损失**。要省空间用 uint8/uint16 截面分位。

## 5. 数据库选型

### 5.1 按数据性质分层（**不要用一种 DB 包打天下**）

| 数据 | 30 万因子下的量级 | 选型 | 理由 |
|---|---|---|---|
| 因子元数据 + 指标 + 血缘 | 30 万行 + 指标长表 ~10⁷ 行 | **PostgreSQL** | 这是"小数据"，PG 绰绰有余；JSONB 存 AST + GIN 索引可查"含某叶/某算子" |
| 因子值矩阵 | 30万 × 5000 × 2500 = **3.75×10¹²** 格 | **文件（h5/parquet），只存入库子集** | 任何 DB 都装不下全量 |
| 近重复 / 相似检索 | 30万² / 2 = **4.5×10¹⁰** 对 | **分桶 + 向量 ANN（FAISS / pgvector）** | 全对全不可行，见 §6 |
| 回测原始输出 | 中等 | 文件（parquet），指标才入库 | |

**"SQL 够用吗？"** → 元数据/指标/血缘：**完全够用，且是首选**。
SQL 不胜任的只有两件事：**因子值宽表**（10¹² 格）和**两两相关**（O(N²)，本质是算法问题，换 DB 无用）。

### 5.2 现状（2026-09-11 核实 qlib_code）

- **目前没有业务库**：SQLite 只用于 mlflow 实验追踪。
- **且已踩过锁坑**：`backend/app/engine/patches/qlib_parallel.py` 注释原文记录过多线程写同一个
  `mlflow.db` 触发 `SQLite "database is locked"`，故改用"线程独立 db"绕开。
- 已装依赖：**SQLAlchemy 2.0.52 / alembic 1.19.1**（迁移工具）/ pymongo 4.17 / redis 8.1 / mlflow 3.15。

### 5.3 结论

- **目标库 = PostgreSQL**（对方已确认将来要上服务器多人写库 → 多写者场景下这是唯一稳妥选择）。
- **迁移成本确实低但不要低估运维**：代码侧 SQLAlchemy 已是硬依赖、alembic 现成，换连接串 + 一次迁移即可；
  但单人本地维护一个 PG 服务是实打实的负担。
- **因此时机建议**：**先不引入数据库**。元数据现在只有 MB 级，JSON/文件 + 单进程写足够撑到 M4/M6；
  等真正出现并发写需求再上 PG（那时迁移成本也不高）。
- ⚠ **过渡期若用 SQLite，必须满足三条**，否则过渡 schema 会变成迁移债：
  ① schema 用 **SQLAlchemy 模型**定义（不要裸 `sqlite3` + 手写 SQL）
  ② 开 **WAL 模式** + `busy_timeout`
  ③ **单写连接**（避免重演 mlflow 那个锁）
- ❌ **不要用 pymongo**（灵活 schema 在这里无价值，聚合性能不如 PG）。

### 5.4 schema 草案（PG；AST 为准，字符串只是渲染结果）

```sql
-- 字典
ops(op PK, arity, axis, params_schema, impl_loop, impl_qlib, impl_jq)
fields(loop_name PK, qlib_name, jq_name, source, freq, dim, pit_kind)

-- 因子主体
factors(id PK, name, ast JSONB, expr_loop, expr_qlib,
        n_ops, depth, leaf_set TEXT[], fam_key, skel_key, leaf_proxy,
        status,            -- draft / validated / deprecated
        source,            -- gen51 / manual / report
        created_at, updated_at, note)

-- 指标长表（多池 × 多频率 × 多成本 × 快照）
metrics(factor_id, pool, freq, cost, seg, snapshot_ts,
        ic, ic_ir, ic_win, ann_ex, dd, calmar, sharpe, turn, neg_yr,
        mono, best_bucket, d1_polluted, n_period,
        PRIMARY KEY(factor_id, pool, freq, cost, seg, snapshot_ts))

-- 血缘
runs(run_id PK, gen, seed, n_cand, params JSONB, started_at, ended_at, engine_ver)
factor_runs(factor_id, run_id, l1_score, l1_ic, l2_pass, sign, admitted)

-- 近重复边（稀疏，只留超阈值）
dups(a_id, b_id, corr, method, ts, CHECK (a_id < b_id))

-- 标签
factor_tags(factor_id, tag)   -- 'style:barra_resv', 'shape:D1_polluted', 'pool:300'
```

关键索引：`GIN(leaf_set)`（查"含某叶子"）、`btree(fam_key)`、`btree(status)`、`btree(snapshot_ts)`。

## 6. 近重复 / 相似检索（30 万因子规模的关键）

O(N²) 全对全不可行（4.5×10¹⁰ 对）。三步：

1. **分桶预筛**：先按 `leaf_set` / `fam_key` 分桶，**只在桶内两两算**
   （loop_code 的 `root_fam` 就是这个思路，天然可复用）。
2. **签名向量 + ANN**：把每个因子的 rank 画像降采样成 **256~512 维**向量（如每 8 个调仓日取一个截面，
   存 float16）→ FAISS / pgvector 找 top-k → **只对候选对算精确相关**。
3. **只写边表**：把 `|corr| > 阈值` 的边写进 `dups`（稀疏）。

---

## 7. 规模约束（真正的问题不是格式，是"存不存"）

- 单因子全历史值 ≈ **50MB**（5000 股 × 2500 日 × float32）→ 1000 因子 = **50GB**，10 万因子 = **5TB**。
- 因此：**值只存"入库 / 活跃"子集**（几百~几千个），其余只留 `ast` + `metrics` + 签名向量，按需重算。
- 需要被索引的只有 **30 万条元数据（MB 级）** + 相似检索向量 —— 都不是瓶颈。
- 文件数：按 `ast_hash[:2]` 或族名分桶，避免单目录几十万文件在 NTFS 上退化。
